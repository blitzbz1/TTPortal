# TTPortal — Android Map / Venue-List Load-Cost Tasks

Derived from [android_map_loading_research.md](android_map_loading_research.md) (2026-06-27, synthesized from 29 adversarial agents across 6 solution families). Each task cites its source section (§), lists concrete files, steps, and acceptance criteria. **Goal:** drastically cut the Android (Galaxy A51) map / venue-list load cost — main-thread `JSON.parse` + clean + sort, peak heap, GC, cold-start wall-clock — **without** crippling Postgres/PostgREST. **Constraint:** migrations 000–099 are FROZEN (new schema ships as 138+); stay inside the existing `{upserts, tombstone_ids, synced_at}` delta + MMKV + MapLibre architecture.

**Conventions**
- **ID:** `T###` — stable references, grouped by Stage (M, 0, 1, 1.5, 2, 3, 4, 5). Stages are dependency-ordered (see **Sequencing** at the foot); tasks inside a stage marked `[P]` touch disjoint files and can run in parallel. Explicit `(dep: …)` lines on a task override stage order where it needs an earlier one.
- **Priority:** `P0` (do first — the measurement gate + the per-domain cache split every later stage rides on) · `P1` (the core drastic-win program: Stages 1, 1.5, 2, 3) · `P2` (the optional latency layer, the deferred server-scale layer, and follow-up measurement/guardrails).
- **Size:** `S` ≤ ½ day · `M` 1–3 days · `L` > 3 days.
- **`[P]`:** parallelizable within its stage — no shared files, no intra-stage ordering dep.
- **Test / TDD rule:** each stage ends with a guardrail/regression task — write it first as the executable spec for the stage's win (e.g. "warm empty-delta hydrate parses once, cleans once, writes zero") and keep it red until the change lands. Jest for app code (`npm test`); render-count / perf asserts under `src/__tests__/perf/`; `npm run deadcode` (knip) gates the dead-export sweeps.
- **Migrations:** new schema ships as **138+** (prod is currently at **137**); **000–099 are FROZEN — never edited**. Reshapes land as NEW functions with 099-style compat shims, not in-place `CREATE OR REPLACE` that breaks shipped clients. Every new RPC / RLS / trigger / generated column adds a consolidated **pgTAP** test, run locally via `npm run test:db` against the prod-parity replay (`supabase start` can't apply the chain); Edge-fn Deno tests via `npm run test:functions`.
- **Types regen:** any new or changed RPC requires regenerating `src/types/supabase.ts` **before** the client code that calls it will typecheck — each migration stage carries an explicit "regenerate Supabase types" task as a hard dep of its service/hook wiring.

## Stage 0 — Split the global cache-schema version per-domain _(S, no migration)_

Today a single global `CACHE_SCHEMA_VERSION = 1` (`src/lib/cacheSchema.ts:12`) is the version gate for **three independent MMKV stores at once**: the cities catalog (`cities-cache-v2`, read at `citiesPersistentCache.ts:38`), every venue scope (`venues-cache-v2`, read at `venuesPersistentCache.ts:49`), and the whole offline KV domain-cache store (`offline-kv-cache`, whose `ensureSchema` IIFE calls `store.clearAll()` on mismatch — `offline-cache.ts:61-72`). Because the three stores share one constant, bumping it for *any one* domain self-inflicts the exact cost this whole effort targets (research §2 "Cache-version blast radius", DO-NOT #1): the 3.35 MB cities re-parse from `since=null`, an every-scope venue re-pull, **and** a full wipe of every domain cache built on `cacheUtils`. This stage replaces the single constant with `CITIES_CACHE_SCHEMA_VERSION` / `VENUES_CACHE_SCHEMA_VERSION` / `KV_CACHE_SCHEMA_VERSION` (each seeded to the current value `1`, so this refactor itself triggers **zero** re-pull), points each reader at only its own, and locks the isolation in with a regression test so later stages (2 reshapes cities, 3 reshapes venues) bump exactly one domain without collateral.

## Stage 1 — Collapse the redundant 3x cities hydrate _(S, no migration)_

On every cold start `LocationProvider` mounts once at app root and `useCitiesQuery` runs **two** code paths back-to-back (`initialData` for the synchronous first paint, then `queryFn` because `refetchOnMount: true` on line 39). It is sequenced ahead of the catalog refactor because it is the lowest-risk, highest-certainty cleanup and de-risks the larger bet.

> **GATE — measure first.** The entire ~7× row-cut headline (3.35 MB → ~105–210 KB, ~430–830 ms A51 JS reclaimed) rests on the eager tier being ~1,500 rows. **This stage's L effort is gated on Stage M measurement** of the live tier size (`SELECT count(*) FROM cities WHERE active AND expansion_status <> 'hidden' AND (venue_count > 0 OR expansion_status IN ('launch_ready','community_review','coming_soon'))`). The cities catalog is the verified #1 Android cold-mount cost: `LocationProvider` (mounted once at app root) drives `useCitiesQuery`, which parses the full ~10,330-row / 3.35 MB blob and then runs a full-catalog `toLocationCity` map + `mergeExpansionCityWave` + `cleanCityCatalog` + two `compareRo` sorts on every change, all consumed *whole* by the switcher. Lazy field materialization can't help — only cutting the **row count** does. ## Stage 5 — (Deferred) Edge/CDN catalog artifacts _(L, migration 141 + `build-catalog` edge fn)_

This is the server-scale layer, and it is **deferred on purpose**. Catalog tiering (Stage 2) already collapses the cities cold `jsonb_agg` ~10–14× and the slim venue delta (Stage 3) trims the per-city pull — so for the foreseeable steady state the RPCs are cheap enough. The CDN pipeline only earns its keep once **cold cross-user aggregation CPU or Storage egress is the *measured* binding constraint** (research §3, §5, DO-NOT #10). Worse, the naive version is a trap: a single venue approval bumps the affected city's `cities.updated_at` via mig 070's `refresh_city_venue_count` (verified: `070_city_venue_count_refresh.sql:23` sets `updated_at = now()`), so a *monolithic* cities artifact would re-hash on every approval during OSM import waves — regressing vs the granular delta. The design therefore materializes the Stage-2 tier and the Stage-3 **per-city** slim venue sets as **content-hashed, immutable Storage objects behind a manifest**, driven by a **per-city debounced dirty-flag** (not a whole-catalog rebuild) with a pg_cron safety-net; clients hash-skip the manifest to do **zero DB work** on a warm boot, and the existing `get_cities_delta` / `get_venues_delta` RPCs stay as the offline/error fallback **behind a flag**. It composes *under* Stage 2/3 — it serves their artifacts and does not redefine them — so it depends on both shipping first. Do not start any task below until T110's gate evidence is captured.

> **Migration numbering:** this stage's schema is written as `141_catalog_artifacts.sql` on the assumption Stages 2–4 consume 138/139/140 (latest on prod is `137_no_blocking_staff.sql`). When you actually create the file, renumber to the next free number after Stages 2–4 land, and keep the assertion file name in lockstep (`supabase/.migration-test/99_assertions_141.sql`).

## DO NOT (carried from research §6)

1. **Do NOT bump the global `CACHE_SCHEMA_VERSION`** — it `clearAll()`s the whole KV domain-cache store + re-pulls cities + every venue scope. Split per-domain first (Stage 0).
2. **Do NOT ship full-catalog columnar JSON** — the Hermes reassembly loop nets ~0–30 ms, possibly negative. Columnar only on the small tier, if at all.
3. **Do NOT use MessagePack/CBOR/CSV/NDJSON** — JIT-less Hermes makes userland decoders lose to native `JSON.parse`; gzip already removes wire redundancy.
4. **Do NOT chase gzip/brotli** — already negotiated transparently; parse runs on the decompressed string; brotli forces a JS decoder. The wire is not the bottleneck.
5. **Do NOT drop `zoom`/`admin_area` from the cities tier** — zoom drives `getMapRegionForCity`, admin_area is the AddVenue `state` field; only `country_name` is derivable.
6. **Do NOT slim venues to "map columns only"** — the map IS the list (address/city/tables_count are read by the sheet + search). Drop only `city_id`/`created_at`/`updated_at`/`approved` (city → `selectedCity.name`); address stays.
7. **Do NOT int/bit-pack venue enums/flags** — ~0 gzip-wire gain, adds a CASE↔lookup drift surface + a per-row decode that re-blocks the JS thread. Keep strings + bools.
8. **Do NOT build any tier/columnar RPC with per-column `ORDER BY`** — shared `updated_at` makes tie order non-deterministic and silently misaligns arrays; build all output in ONE aggregate over a single `row_number()`-ordered CTE.
9. **Do NOT adopt expo-sqlite as the cities fix** — doesn't remove the first-install parse, doesn't scale to 100k, needs the same refactor, reverses T047, re-adds a web fork.
10. **Do NOT build the CDN pipeline yet** — the monolithic cities artifact re-hashes on any venue approval (mig 070). Defer and compose under catalog.
11. **Do NOT implement viewport/bbox as a replacement for the city venue delta** — saves ~nothing at default zoom and breaks the whole-scope invariant the GPU clusterer relies on. Additive zoomed-in path only.
12. **Do NOT fold `has_coach` without a coach→`venues.updated_at` trigger**, and **do NOT fold per-user `unvisited` into shared rows / a city_id-only cache** (cross-user leakage on a shared device).
13. **Do NOT gate `search_cities` at <3 chars on a pg_trgm GIN index** — trigrams need ≥3 chars; use a `name_norm` prefix btree, and always debounce + min-length.
